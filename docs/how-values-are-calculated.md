# How the values are calculated

- Account snapshots are authoritative **as observed**, not live service balances. Ingestion time never refreshes observation time. The CLI cannot verify the currently authenticated account without credentials; it uses only retained account-response evidence.
- Remaining reported credits are `max(reported credit limit - observed CREDIT usage, 0)`. This uses the reported limit from the latest account snapshot; whether it includes bonuses or add-ons is unverified, so total available credits remain unknown. Populated extra-credit schemas are unsupported and stay separate.
- Available per day is remaining reported credits divided by remaining seconds until explicit reset, converted to UTC 24-hour days. This allocation is truncated to six decimals for presentation. It is not a forecast, burn rate, historical daily measurement or local-calendar-day allowance. Stale, future, expired-reset or unknown-reset observations cannot supply this allocation. Stale remaining reported credits are explicitly an as-of calculation.
- The extension (not the CLI) also shows **today's allowance**: the remaining reported credits at the first comparable update of the local day, divided by the sum of budget-day weights up to the reset (a budget day counts 1, the reset day only its part before the reset, other days 0; `bobert.budgetDays` chooses the days, default all seven). **Used today** is the usage at the latest update minus the usage at that first update, an observed lower bound because earlier usage that day is unknown, not zero. Both use the local calendar day of the device time zone. The 24-hour figure above is unchanged and remains what the CLI reports.
- Missing fields stay unknown. Integer fallback is labeled `reduced_precision`. Reset-field conflicts preserve unknown reset. Equal-time billing conflicts withhold a selected observation.
- Advancing reset metadata indicates an observed cycle change. A same-reset decrease is an anomaly/adjustment; a changed reported limit suspends comparisons. Cross-cycle deltas and consumption across observation gaps remain unknown. Nothing sums account snapshots with sessions.
- Multiple account partitions or observations without a supported identity withhold the account view. There is no account selector or automatic inference of the active login in this milestone.
- While no forecast is eligible, the credit view shows credits left, days to the reset and the daily allowance (remaining reported credits divided by time to the reset). It may add an *at-least* average since the cycle start: latest usage divided by the time since the cycle start, which is the evidence-backed start or, **under the assumption that a cycle lasts at most 31 days**, the reset minus 31 days. Kiro does not document when a cycle starts; the figure is a lower bound, not a forecast.
